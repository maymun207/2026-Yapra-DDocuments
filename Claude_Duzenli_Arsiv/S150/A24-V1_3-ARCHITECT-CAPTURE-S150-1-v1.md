## 1 · The thesis, in the document's own terms (READ)

Today, understanding (stage 03), tool selection (stage 07) and scope (stage 09) are built on ONE backend's world, and none of the three gates reads anything DERIVED from a connected backend. In the target state all three read the CAPABILITY CARD: a machine-derived object per connected backend, built ON TOP OF the eval-gated governance kinds that already exist (entity_alias, glossary_term, metric_definition, metric_registry, tool_annotation, routing_hint, blind_spot, persona_fragment, gateway_tool_policy, agent.param) by adding new derived kinds (tool_profile, slot, corpus_entry, calendar, output_contract, web_card) through the SAME governance path (draft → gate → publish, audit, rollback) — never a second parallel store (12.6).

"Connected" is redefined as a CONJUNCTION: routing exam (offline, no tools/call) ∧ live reach probe (read-only canary tools/call). A composite task runs as a PLAN written by a planner and executed by a DETERMINISTIC executor; every number that reaches the user's eye is a tool byte. Learning improves only FINDABILITY (examples, aliases, wording, base set, default plans), never what a tool DOES, and never learns from an empty result.

Color key (READ, §0): purple = LLM/probabilistic · teal = deterministic gated code · grey = pipeline backbone (unchanged) · amber = derived data, regenerated at every sync · blue = user/owner decision · red = today's defect / removed.
