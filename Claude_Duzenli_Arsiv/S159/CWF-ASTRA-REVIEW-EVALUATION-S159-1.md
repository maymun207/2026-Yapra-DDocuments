## 3 · What Astra ADDS beyond A24 v1_3 and the scout delta (carried into v2 by name, EXT-DESIGN-S159-ASTRA-1)

A1 · THREE CLASSES OF GOVERNED DATA (replaces the draft's P2): (i) AUTHORITY CONSTRAINTS — tenant, user scope, read/write right, data access: binding; retrieval and the LLM cannot cross them (A24 authorization layer; RBAC lens). (ii) EXPLICIT ROUTING OBLIGATIONS — scoped rules the owner publishes: "under condition X, capability Y must be EVALUATED (offered)". Obligations are counted against the tool budget FIRST; if obligations alone exceed router.maxTools the turn is stamped OBLIGATION-OVERFLOW and the owner sees it in the Rules tab — never a silent overflow, never a silent drop. (iii) RELEVANCE HINTS — keywords, metric hints, predicted entity layer, past success, sticky context: EVIDENCE for ranking, never a verdict. INVARIANT: every valid governed hint is evaluated on EVERY path and its effect on the decision is recorded in the trace; no hint crosses an authority boundary; candidacy does not force offering. MIGRATION DEFAULT (for the owner's ruling): every existing PUBLISHED tool_category keyword row is classified OBLIGATION at migration (nothing the owner entered loses force — "SAKIN … TEK bir fonksiyonalite ÇIKARTMAYACAKSIN"); the shadow stage measures how often obligations overflow the budget; the owner downgrades rows to HINT in the UI where the measurement shows it. This preserves the owner's law "probabilistic selection never overrides the deterministic rules I entered" AND Astra's budget invariant.
A2 · PROVIDER OFFERING MATRIX: the offered set is specified per provider (Anthropic full-catalogue cache path; OpenAI/Gemini filtered path), with the cost profile of each measured in the baseline stage; the same governed obligations and authority constraints apply on both; the discovery chain (A5) behaves identically on all three.
A3 · TOOL IDENTITY = server_id + backend_id + tool everywhere; model-facing name derived and collision-free; F-S159-TOOL-IDENTITY-NAME-ONLY-1.
A4 · GOLDEN/PUBLISH GATE GENERALISED to tool_category, routing_obligation, ranking_policy and card rows (wiring of decideGoldenPublish; governance.ts:429).
A5 · DISCOVERY CHAIN for the meta-tool: find → authoritative card → current schema → register → usable in the NEXT model step; identical on three providers; each use classified INITIAL-NEED-MISS (the need was in the first message) vs NEXT-STEP-DISCOVERY (the need arose from a result) — only the former feeds the miss ledger (A24 L5, item 9).
A6 · ROUTING EVENT (extends K24, one schema): per turn × tool: candidate? offered? selected? call sent? args/scope correct? result empty/partial/complete? contributed to task success (K23 conjunction)? + catalog_version, policy_version, model, index_build_id. tool_experience becomes a DERIVED view of this event stream (fixes C14 by construction).
A7 · AGGREGATION FACE on cards (D3) and COVERAGE face on knowledge cards (D11).
A8 · RUNTIME BUDGET stays beside the plan (D4): executor fan-out in code, one result table, declared step/token budget, partial≠complete stamps; the model never receives raw per-factory payloads.
A9 · EVIDENCE STAGES replace dates: E1 evaluation ground (held-out labelled tasks with acceptable-set labels and alternative valid chains; baseline on three providers) → E2 catalog & policy contract (identity, provenance, authority, output/aggregation semantics, version group) → E3 shadow comparison (today's matrix path · matrix off · lexical · dense · hybrid · reranker, same tasks, named arms) → E4 discovery-plan-execute integration (new tools really usable, dependency coverage, controlled fan-out, partial correctness) → E5 learning + controlled publish (events, independent test, canary, group rollback) → removal of the matrix path.
