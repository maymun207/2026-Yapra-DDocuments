1 · What changed

Why v0_2 no longer holds

v0_2 was written before SPINE-FRONT and before cwf_yaprak proved, in code, that it is a configurable multi-backend agent platform. Three of its load-bearing claims are now wrong. The brick layer is still zero-hit in the canonical repo (DR-4) — which means correcting it now is free, and correcting it after the merge wave is not.

agent-runtime was mis-specified

v0_2 made LangGraph the single conversational brain. SPINE-FRONT inverts this: the CWF turn pipeline owns the user; LangGraph is a workflow engine behind the MCP boundary. One foundation brick becomes two.

"One Langfuse" broke Class C

SC-4 says one Langfuse; the telemetry contract says prompts never cross the perimeter. Both cannot hold for a sovereign silo. Resolved in §7: one Langfuse configuration, per-instance deployment.

The product axis was missing

v0_2 had no Web Asistan manifest (the G4 default first product) and no ARMES column. It also had no name for the thing that makes one product differ from another. That thing is now profile.cue.

The runtime's substrate is temporary

cwf_yaprak lives on Vercel + hosted Supabase for convenience. Tomorrow it runs in a container against EAIP's own Postgres, talking to EAIP bricks. §10 budgets that port honestly.

2 · The two axes

The organising idea of v0_3

Every complexity fear about "one codebase serving many services" dissolves the moment two axes stop being called by the same word. They are orthogonal, they compose, and each is already half-solved.

one codebase → one release lifecycle → N deployments → M backends per deployment

The N axis (products). A product is a deployment. It has its own tenancy tier, telemetry tier, channels, golden suite, and customer perimeter. GU is pooled·full-export; CWF is silo·class-ab; Insurance is silo·sealed. These tiers are mutually incompatible — they cannot share a deployment.

The M axis (backends). A backend is an MCP data source inside one deployment. ARMES is a backend. Superset is a backend. They coexist in the same running instance, discovered and scoped per request.

M — solved, in production shipped

cwf_yaprak P4.7: backend identity is first-class DATA (backends table + FK); adding a backend is a row, not a migration. Proven by two live packs (prompt/backends/armes, prompt/backends/superset), a kind registry with CORE (Zod-locked) and SOFT (DB-editable) classes, a backend-agnostic prompt core plus backend-aware assembler, and per-backend RBAC scoping. Roadmap P7+ already names the target: "more backends behind the same seam; per-tenant scoping."

N — this document's job to build

The runtime becomes a container brick in an EAIP instance: it binds to EAIP's data-core (Postgres, not hosted Supabase) and speaks to the other EAIP bricks over MCP. One instance per product. Product difference is expressed only through profile.cue — never through product-conditional code, never through a fork.

The composition rule

Many tenants inside one instance; never many products inside one instance. GU's thousands of shops share one pooled deployment (Keycloak Organizations). GU and CWF never share a deployment. This is not a preference — it is what the tenancy and telemetry tiers already say, and it is what makes the insurance firewall (defined as the absence of manufacturing bricks) structurally true rather than merely intended.

3 · Principles

Purposeful bricks on an immutable substrate

Everything is a file in the fleet repo — from the operating system of a node to the profile of a product. One repo, one approval gate, one audit trail. v0_2's five principles hold; three are added.

Foundation vs capability

Foundation bricks are singletons per instance. Capability bricks declare dependencies on foundation contracts; they never own shared infrastructure.

Brick contract

Versioned inputs, outputs, registered MCP tools, semver — now a machine-checked CUE schema, not a convention (§8).

Release BOM

An EAIP Release pins tested-together brick versions. Promotion into a BOM is gated on attestation and per-profile golden canary (§9).

Granularity test

"Ships in one product but not another?" Yes → brick. No → internal detail of a brick.

Whose cluster, whose controls

Management channels end at ownership boundaries. Customer perimeters are pull-only via the fleet repo, gated by customer PR approval.

Configuration, not forks NEW

Product difference is declared in profile.cue. Product-conditional code in the runtime is a contract violation, rejected in CI.

Closed topology, governed content NEW

The runtime's stage list, prompt-segment ids, and CORE kind schemas are closed code sets. Governance edits their content, never their topology. (The pattern cwf_yaprak already enforces.)

Escape hatch = MCP NEW

A need that will not fit the schema goes one of two ways: a kernel PR into the closed stage set, or across the MCP boundary into LangGraph. Never a free-form hook in YAML.

4 · The assembly model

Six nested definition layers, all in git

fleet repo
One directory per instance. The management brain. PR merge = the only write path into any environment.
instance manifest
Deployment identity: brick list, release pin, tenancy tier, telemetry tier, customer values. The N axis.
product profile NEW
Runtime identity: channels, enabled stages + params, prompt segments, kind families, backend rows, models, retrieval profile, trust/quota policy, golden suite. The M axis + the product's behaviour.
release BOM
eaip-YYYY.N — tested-together brick versions. Manifests reference it; never loose brick versions. Promotion is gated (§9).
bricks
OpenTofu module + Helm chart + brick.cue per brick; OCI artifacts in Harbor, signed and SBOM-bearing; materialized by ArgoCD app-of-apps.
machine configs
Node OS config per node. The OS itself is a declarative file — no SSH, no drift, no snowflakes. (Substrate pilot-gated: D1.)

Birth sequence of an instance

  1. Open instances/<name>/ in the fleet repo: manifest + profile + machine configs + values.
  2. OpenTofu boots nodes and applies machine configs — the cluster exists.
  3. Bootstrap ArgoCD (infra-core) pointed at the instance directory and Harbor. Outbound-only; zero inbound access.
  4. App-of-apps materializes the 10 foundation bricks, then capability bricks per manifest. Admission control verifies signature + SBOM before any image runs (§9).
  5. tenantprov runs day-1: realm/Organizations, schemas, routes, collections per tenancy tier.
  6. conversation-runtime seeds itself from the profile: backend rows, kind registry, prompt segments, agent params, trust ceilings — the profile is the seed, the DB is the running state.
  7. fleet-control (ARDICTECH side) registers the instance: heartbeat expectation armed, BOM recorded.

Every subsequent change — app version, K8s version, OS version, profile content — is a PR to the instance directory, merged on customer approval, synced by ArgoCD. One gate for all four change classes.

Resolving the SC-4 ↔ Class C contradiction

SC-4 says one Langfuse. The Class C contract says prompts never leave. For a sovereign silo both cannot be true of a single central instance. The resolution is a distinction v0_2 did not draw: one Langfuse configuration and host-trust posture (ADR-007), deployed per instance. Traces stay inside the perimeter; only Class B aggregates — including canary verdicts — cross. "One Langfuse" is a statement about uniformity, not about centralisation. The AWS-hosted instance the CWF line uses today is a development convenience, not the deployment model.

Sealed instances disable A and B. Consequence written into the sealed contract: outage detection is the customer NOC's obligation and support SLA is priced accordingly — a dead-man switch cannot hear a heartbeat that is never sent (D5).

8 · Contracts

Two schemas and one rule that binds them

This is the section that turns "brick" from a slide into a system. Until these exist, the brick contract is a convention and the release BOM is a YAML list. (SOTA gap 5.)

brick.cue — the packaging contract

// every brick ships one. CI rejects a brick without it.
#Brick: {
  name:        string                        // stable id
  version:     =~"^\\d+\\.\\d+\\.\\d+$"        // semver
  class:       "foundation" | "capability" | "control"
  requires:    [...#BrickRef]                // declared deps on foundation contracts only
  provides: {
    mcpTools:  [...#McpToolDecl]             // name + input/output schema + trust class
    schemas:   [...string]                   // data-core schemas it leases
    endpoints: [...#Endpoint]
  }
  tiers: {
    tenancy:   [..."silo" | "pooled"]        // which tiers it supports
    telemetry: [..."full-export" | "class-ab" | "sealed"]
  }
  supplyChain: {                              // §9 — no exceptions
    signed:    true
    sbom:      string                        // artifact ref
    provenance:string                        // SLSA attestation ref
  }
}

profile.cue — the product contract

// one per product. The ONLY place a product may differ.
#Profile: {
  product:   string
  channels:  [..."web" | "whatsapp" | "teams" | "email" | "voice"]
  stages:    { [#StageId]: { enabled: bool, params?: {...} } }   // CLOSED set — code
  prompts:   { [#SegmentId]: string }                          // 20 enum-locked ids; TEXT is governed
  kinds:     { core: [...#CoreKindRef], soft: [...#SoftKindDef] }
  backends:  [...#BackendRow]                                // ← the M axis
  models:    { router: "litellm", providers: [...#ProviderRow] }
  retrieval: { rag?: "light" | "full", graph?: bool }
  policy:    { trustCeilings: {...}, quotas: {...}, guardrails: [...#GuardrailId] }
  rollout:   { strategy: "direct" | "progressive", guardrails?: {...} }
  golden:    { suite: string, minTurnsPerArm: int }        // ← §9 gate input
}
// NO free-form escape: no `script:`, no `customHook:`, no embedded expressions.
// A need that will not fit → kernel PR (closed stage set) or an MCP tool (workflow-runtime).

The binding rule — manifest ↔ profile consistency

Every backend a profile declares must map to an MCP brick the instance manifest deploys. A backend row pointing at a brick that is not in the manifest is an undeployable product, and CI rejects it. This single rule is what fuses the two axes: the manifest says what exists in this perimeter, the profile says what the runtime is allowed to reach, and they must agree. cwf_yaprak already enforces the in-repo version of this with a foreign key on backends(id); v0_3 promotes it to the fleet-repo level.

What "product-conditional code" means, precisely

Forbidden in the runtime source: branching on product identity (if (product === 'GU')), per-product branches, per-product forks. Permitted and expected: new closed-set stages, new CORE kind schemas, new channel adapters, new backend packs — all of which are kernel changes that every product inherits and every product's golden suite must survive. The discipline is already in the codebase ("the id set is CLOSED… governance edits segment TEXT, never segment TOPOLOGY"); profile.cue makes it enforceable one level up.

9 · The release train

BOM promotion gate

One kernel now carries every product. That inverts the blast radius: a runtime regression hits all N products at once. Two mechanisms hold the line, and both are gates on entry to a release BOM — not recommendations.

GateConditionStatus
Chain of custody Every brick artifact is Cosign-signed, carries an SBOM and SLSA provenance from CI; Kyverno admission refuses anything unsigned or SBOM-less. The BOM records the attestation refs. CRA reporting obligations ≈Sept 2026. absent both sides (DR-8) — SOTA gap #1
Per-profile canary A conversation-runtime version enters no BOM until every active profile's golden canary returns a green verdict — longitudinal Wilson CIs, goldenSetHash-matched baseline, "underpowered never phrased safe". L3 exists in-house — port, not design

The bill for one kernel

Eval cost now grows linearly with product count: each profile needs its own golden suite, curated by people who know that product's domain. This is the price of the single codebase and it must be budgeted, not discovered. It also reclassifies SOTA gap 3 (port L3 → release train) from "would be nice" to load-bearing: without it, the N-axis is an unmonitored fleet of shared-kernel deployments. The canary verdict is a Class B aggregate — it crosses the perimeter, so fleet-control can see a red profile without seeing a single prompt.

10 · The container port

Vercel + Supabase → container + data-core

The runtime's current home was chosen for speed, not architecture. The port is not a Dockerfile. It is a set of semantic changes, because serverless assumptions are baked into behaviour. Budget it honestly or it surfaces as a surprise in a sovereign install.

ItemWhat actually changesClass
Warm caches The OBS-1 epoch bump was designed to "self-cold every warm serverless instance without a redeploy" — i.e. invocation lifetime was a natural cache ceiling. In a long-lived container that ceiling disappears: the epoch becomes the only invalidation path. Provider registry, trust registry, knowledge provider, MCP discovery cache — each needs its invalidation semantics re-verified under a process that lives for days. medium
Flush ordering forceFlushObservability() runs sequentially before res.end() because serverless freezes the process after the response. A container has a real background exporter — the cost can be removed. A gain, not a burden, but only if taken deliberately; otherwise we keep paying latency for a constraint that no longer exists. small (net win)
SSE + heartbeat + timeouts Built against a function timeout. No timeout in a container; different failure modes (connection leak, unbounded stream). Needs explicit limits. small–medium
Supabase → Postgres (DB) Straight port to data-core Postgres 16. Migrations already SQL. small
Supabase → Postgres (RLS) Policies are largely portable; what is Supabase-specific is the auth.uid() family. Needs a session-context shim mapping the authenticated principal into Postgres. The service-role-only tables (golden specimens, routing audit) map to a dedicated role. medium
Supabase Auth → Keycloak The one real rewrite (SC-2). Authority moves to Keycloak/OPA; the capability matrix survives as authorization semantics, mapped to realm roles and OPA policies. A mapping table is a deliverable. Kale = Entra federation (D8). medium–large
Packaging Container + Helm chart + brick.cue; profile-as-seed on first boot; signed image (§9). medium

Precondition, not a nice-to-have: a sealed insurance instance and a sovereign Kale silo cannot reach hosted Supabase. Until this port lands, conversation-runtime is an excellent Vercel product and cannot be an EAIP brick.

13 · Decision records

Choices made, gates defined

D1 — Cluster substrate: Talos Linux · pilot NOT YET RUN · deadline set

Immutable, API-only OS (no SSH, no shell, no package manager); OS+K8s lifecycle as one declarative action; CIS hardening built in; native fit for sealed offline-bundle upgrades. Status 2026-07-13: the pilot has not been run. v0_3 is written so that this does not block: nothing above cluster-substrate depends on the verdict — everything upward is plain Kubernetes, so the verdict swaps exactly one brick and zero contracts. Gate: two-week staging pilot; the team must sustain API-only debugging; GU/ARMES workloads must show no friction. Deadline: before the first customer perimeter is provisioned (Kale CWF, M7) — after that, a substrate change stops being a brick swap and becomes a rebuild of a live customer cluster. Fallback (not shameful): RKE2 + Rancher. What the fallback costs: not architecture — narrative. "There is no SSH to audit" is a sentence that earns money in defence and insurance conversations. RKE2 gives it back.

D2 — No Rancher for customer perimeters · 3-condition re-evaluation gate

Rancher's persistent agent channel is remote control into the customer cluster — incompatible with the PR-approval promise and defence accreditation. Re-open only if all three hold: (1) ARDICTECH-operated clusters > ~10–15, (2) heterogeneous infra, (3) ops team large enough to need a central UI/RBAC as a first-class tool. Even then: own clusters only.

D3 — Omni deferred · licensing stance

Omni server is BSL-1.1; production use needs a commercial licence. OSS-first, same reflex as Terraform-BUSL → OpenTofu: start with talosctl + OpenTofu Talos provider + Headlamp. A deliberate purchase decision later, not a default dependency.

D4 — Fleet repo is the management plane · pull-only

Git as brain: instance directories, PR merge as the single write path, customer approval as a first-class merge gate, ArgoCD pull as the single sync mechanism. Zero inbound access. Sealed variant: signed offline bundles from the same directories. Comfortable to ~50 instances.

D5 — Sealed-customer NOC obligation · contract clause

Where telemetry is sealed, outage detection is contractually the customer NOC's duty and support SLA is priced for blind operation.

D6 — conversation-runtime is a foundation brick; CWF is a profile · NEW · supersedes agent-runtime

Follows SPINE-FRONT and the A6 amendment: one conversational runtime serves every channel; LangGraph orchestrates behind the MCP boundary and never addresses the user. The brick therefore cannot carry a product's name — cwf_yaprak as a brick id would leak product semantics into the kernel and licence the first fork. Resolves the ADR's internal inconsistency (§5 A6 text = foundation; §6 seam-9 "cwf_yaprak brick, silo tier" = capability): the A6 text wins; seam 9 is relabelled. Falsification gate — Web Asistan: WA must stand up with zero product-conditional lines in the runtime — configuration, a channel adapter, and a segment set only. Pass ⇒ the general-front-agent thesis is proven on the cheapest product. Fail ⇒ we learn it for the price of WA, not for the price of CWF. Honest residual risk: whether GU's WhatsApp/voice/asynchronous usta flow sits cleanly on a pipeline designed for factory chat is unknown. WA surfaces that early; GU is deliberately second.

D7 — Two axes, never conflated · NEW

N = deployments (products; incompatible tenancy/telemetry tiers ⇒ never co-resident). M = backends (MCP sources; co-resident by design, added as a row). The word "service" is banned from architectural prose without an axis qualifier. Enforcement: the §8 binding rule (every profile backend must map to a manifest brick).

D8 — Langfuse per instance · NEW · resolves SC-4 ↔ Class C

One Langfuse configuration and host-trust posture (ADR-007), deployed inside every perimeter. Traces are Class C and never leave; canary verdicts are Class B and do. "One Langfuse" is uniformity, not centralisation. The AWS-hosted instance in use today is a development convenience.
