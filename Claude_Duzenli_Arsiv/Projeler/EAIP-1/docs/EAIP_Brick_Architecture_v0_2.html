EAIP brick architecture

EAIP_Brick_Architecture_v0_2 · supersedes v0_1 · derived from Platform v5.1 SSoT · July 2026
1 · Principles

Purposeful bricks on an immutable substrate

v0_2 integrates the cluster-substrate decision (Talos Linux), the fleet management plane, and telemetry/tenancy tiering into the v0_1 brick model. The unifying idea: everything is a file in the fleet repo — from the operating system of a node to the brick list of a product. One repo, one approval gate, one audit trail.

Foundation vs capability

Foundation bricks are singletons per instance. Capability bricks declare dependencies on foundation contracts (a schema, a realm, a Vault path); they never own shared infrastructure.

Brick contract

Versioned inputs, outputs, registered MCP tools, semver. The syscall-table discipline applied to infrastructure.

Release BOM

An EAIP Release pins tested-together brick versions. Instances ride the release train; the eval harness runs per manifest.

Granularity test

"Ships in one product but not another?" Yes → brick. No → internal detail of a brick.

Whose cluster, whose controls

Management channels end at ownership boundaries. ARDICTECH-owned clusters get full central control; customer perimeters are pull-only via the fleet repo, gated by customer PR approval.

2 · The assembly model

Five nested definition layers, all in git

fleet repoOne directory per instance. The management brain. PR merge = the only write path into any environment.
instance manifestProduct identity: brick list, release pin, tenancy tier, telemetry tier, customer values.
release BOMeaip-YYYY.N — tested-together brick versions. Manifests reference it; never loose brick versions.
bricksOpenTofu module + Helm chart per brick, OCI artifacts in Harbor, materialized by ArgoCD app-of-apps.
machine configsTalos machine-config YAML per node. The OS itself is a declarative file — no SSH, no drift, no snowflakes.

Birth sequence of an instance

  1. Open instances/<name>/ in the fleet repo: manifest + Talos machine configs + values.
  2. OpenTofu (Talos provider) boots nodes from the Talos image and applies machine configs — the cluster exists.
  3. Bootstrap ArgoCD (infra-core) is pointed at the instance directory and Harbor. Outbound-only; zero inbound access.
  4. App-of-apps materializes the 9 foundation bricks, then capability bricks per manifest.
  5. tenantprov runs day-1: realm/Organizations, schemas, routes, collections per tenancy tier.
  6. fleet-control (ARDICTECH side) registers the instance: heartbeat expectation armed, BOM recorded.
  7. Every subsequent change — app version, K8s version, OS version — is a PR to the instance directory, merged on customer approval, synced by ArgoCD. One gate for all three upgrade classes.

5 · Fleet plane — the ARDICTECH side

One control brick that never ships to customers

fleet-controlNEW
Runs only on ARDICTECH infrastructure. Monitoring face: Class A/B telemetry receiver, dead-man rules (absence of heartbeat = the alarm), per-instance cost anomaly views. Management face: fleet-repo state — which instance is on which BOM pin, which PRs await customer approval, last sync per instance. v1 UI = Grafana panels; no bespoke frontend.
Prometheus remote-write receiver · Grafana (fleet views) · dead-man ruleset · BOM inventory (from ArgoCD status)

ClassContentCrosses perimeter?Mechanism
A — heartbeatAlive, version, last backup OKyes (default)push, minimal cardinality; absence triggers dead-man alarm
B — aggregatesp95 latency, error rates, token/cost totals, quality-scan pass %contract opt-inPrometheus remote_write, labels stripped, zero payloads

Sealed instances disable A and B. Consequence written into the sealed contract: outage detection is the customer NOC's obligation, and support SLA is priced accordingly — a dead-man switch cannot hear a heartbeat that is never sent.

8 · Decision records

Choices made, gates defined

D1 — Cluster substrate: Talos Linux · pilot-gated

SOTA choice over the management-platform paradigm: immutable, API-only OS (no SSH, no shell, no package manager), OS+K8s lifecycle as one declarative action, CIS hardening built in, materially lower ops/security TCO. Strong sovereign/defense narrative ("there is no SSH to audit") and native fit for sealed offline-bundle upgrades. Gate: two-week staging pilot — team must sustain API-only debugging; ARMES/GU workloads must show no friction. Fallback (not shameful): RKE2 + Rancher, the conservative pair.

D2 — No Rancher for customer perimeters · 3-condition re-evaluation gate

Rancher's persistent agent channel is remote control into the customer cluster — incompatible with the PR-approval promise and defense accreditation. Re-open the discussion only if all three hold: (1) ARDICTECH-operated clusters > ~10–15, (2) heterogeneous infra (bare-metal + VM mix), (3) ops team large enough to need central UI/RBAC as a first-class tool. Even then: Rancher on own clusters only; customer perimeters stay fleet-repo.

D3 — Omni deferred · licensing stance

Omni server is BSL-1.1; production use requires a commercial license (converts to MPL after 4 years). OSS-first stance, same reflex as the Terraform-BUSL → OpenTofu call: start with talosctl + OpenTofu Talos provider + Headlamp. Omni becomes a deliberate purchase decision if fleet ops pain grows — not a default dependency.

D4 — Fleet repo is the management plane · pull-only

Git as brain: instance directories, PR merge as the single write path, customer approval as a first-class merge gate, ArgoCD pull as the single sync mechanism. Zero inbound access to customer perimeters. Sealed variant: signed offline bundles derived from the same directories. Scales comfortably to ~50 instances; beyond that, revisit (see D2).

D5 — Sealed-customer NOC obligation · contract clause

Where telemetry is sealed, outage detection is contractually the customer NOC's duty and support SLA is priced for blind operation. Prevents the "system was down for three days and nobody noticed" invoice landing on ARDICTECH.
