🔒 The secret boundary — the one invariant this diagram proves at a glance

Every secret — MCP server tokens, the service-role key, the LLM provider keys — lives ONLY server-side, in Vercel's env + the server-side MCP resolution. The browser ever holds just the signed-in user's JWT. So no browser edge (cyan/green) carries a secret; only the server-side edges (gold/violet/purple) do. The chat request body is literally { message, history, language, conversationId } + Bearer — proven in the JS bundle and request payload.

How the browser reaches Supabase

Direct but narrow: Auth (sign-in → JWT), RLS-SELECT reads, and exactly two owner-CRUD writes — mcp_settings upsert and conversations rename/soft-delete. Every governed write detours through /api/admin/*; messages are written only server-side. RULE 11: server-only tables REVOKE anon+authenticated writes so a stray client write hard-fails (42501), not a silent no-op.

The agent lives inside Vercel

"Agent" isn't a separate server — it's the _lib code in the same serverless function as chat.ts. The host holds the secrets; the core uses them (service-role for DB, resolved tokens for MCP, env keys for LLM). The trustRegistry reads tier/authority/scope but does not route answers yet — enforcement is Phase C.

Both backends live · flat vs gateway

ARMES = flat (~142 tools, system_of_record). Superset = gateway (search_tools/call_tool, reporting_mirror — authoritative for nothing; scope = bound datasource, never the title). Both edges solid: knowledge-governed and live. A new backend lands at the trust floor (unverified) until declared.
