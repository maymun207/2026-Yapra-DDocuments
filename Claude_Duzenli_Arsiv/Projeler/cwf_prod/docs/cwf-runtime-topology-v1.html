🔒 The secret boundary — the one invariant this diagram proves at a glance

Every secret — MCP server tokens, the service-role key, the LLM provider keys — lives ONLY server-side, in Vercel's env + the server-side MCP resolution. The browser ever holds just the signed-in user's JWT. So no browser edge (cyan/green) carries a secret; only the server-side edges (gold/violet/purple) do. The chat request body is literally { message, history, language } + Bearer — proven in the JS bundle and request payload.

Two ways the browser reaches Supabase

Direct, but narrow: Auth (sign-in → JWT) and RLS-SELECT reads (own mcp_settings; the admin panel's telemetry/users/backends, scoped by role). Every governed WRITE detours through /api/admin/* so the gate + audit run — the browser never mutates domain_rules.

The agent lives inside Vercel

"Agent" isn't a separate server — it's the _lib code running inside the same Vercel serverless function as chat.ts. The host holds the secrets; the agent core uses them (service-role for DB, resolved tokens for MCP, env keys for LLM).

Flat vs gateway backends

ARMES = flat (~142 tools listed directly). Superset = gateway (search_tools/call_tool over ~22) — registered in backends but its domain pack + adapter are P6, so its edge is dashed (wired, not yet knowledge-governed).
