CWF · EAIP — detailed design · LLM control surface

Where we steer the model — every control point, its data source, and how hard it binds

rev 1 · 2026-06-28
HEAD a8bd531
code-grounded
The system is a deterministic control sandwich wrapped around a non-deterministic core. We constrain the input as much as possible (what the model may see), call the stochastic model under hard call limits, re-impose determinism on the output (what we do with what it said), and gate the data that feeds the input levers. The model is free only in the middle — only at routing + prose, never at correctness. This document enumerates the 13 control points, the DB table (or code) behind each, and — the load-bearing distinction — whether each is HARD (the model cannot violate it) or SOFT (a request it may ignore).

Reading model · three axes

axis 1 — moment (when we steer)
INPUT what the model is allowed to see — the primary lever, before generation.
CALL how it generates — provider, temperature, token & loop caps.
OUTPUT what we do with what it said — checks & corrections, after generation.
WRITE-META what may enter the input-control data — the controller of the controller.
axis 2 — binding (how hard)
HARD deterministic; the model physically cannot violate it (tool not offered, mandatory time tool, gate, RLS, capped params).
SOFT advisory; a prompt request or a measure-don't-block. The model can ignore it.
GAP no control exists yet — a named hole, not a guarantee.
axis 3 — source (what's behind it)
DB · table governed data, runtime-editable via the gated publish path.
code-fixed pinned in source — changing it needs a deploy (by design, for identity/safety/limits).
none derived from NTP / the live request — no stored table.

The finding this lens forces into the open

⚠ empty≠zero is guarded by TWO soft controls and ZERO hard runtime blocks

Trace the IKINCILUST blind-spot across the surface: it is a prompt instruction at CP1 (soft — the model may ignore it) and a measured-but-not-blocking check at CP9 (soft — it records, doesn't retract). There is no hard runtime gate that stops a false "sıfır fire" from reaching the user. That is the structural reason the ARMES-on acceptance test still tracks model capability: 3/4 models honoring the blind-spot is not a guarantee the architecture enforces — it is the strongest model complying with a soft request.

This is not a bug to patch casually — it's a deliberate current state with two named fixes already on the roadmap (CP11/Phase F for the blank-answer path, CP12/P7 for a Superset runtime validator) and a deeper answer (Phase D redundancy — a single self-consistent in-scope lie is made harmless, not detectable, without a second source). The control surface simply makes the soft/hard split impossible to overlook.

Design principles this surface encodes

The model is the authority on routing + prose, never correctness

Every correctness/safety lever (CP3, CP5, CP8, CP10, CP13) is HARD and deterministic. The model's freedom is fenced to which tool and how to phrase.

DB-governed where values must flex; code-fixed where identity must not

Knowledge values (CP1) and scopes (CP3) are gated-DB. Identity, safety, time, call-caps, and the gate logic itself (CP2, CP5, CP8, CP13) are code — you cannot hot-swap safety from a row.

Inject hard, comply soft — so gate the injected data

CP1 is definitely present but obeyed only by grace. The architecture's answer isn't "trust the model" — it's CP13: make the data the model is told gate-clean, shape-locked, and resettable.

Output determinism is real but post-paint

CP9/CP10 re-impose determinism, but streaming means the user may see a violation before the correction. Closing that needs CP11/CP12 and, ultimately, redundancy (Phase D).
