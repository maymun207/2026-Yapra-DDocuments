OA-10 · Control-Plane UI Home · Redesign Scope

The house the control plane lives in A govern-plane / microscope-plane split, five panels specified, so F-obs lands into a clean home — not the flat 9-tab admin it is today.

Today's admin is a flat stack of nine tabs — govern, observe and tweak all mixed, tables that clip text and don't expand, 15-digit costs, no lifecycle legibility. The bar is clean, mainstream, SOTA — and the standing instruction holds: don't reinvent America. Adopt the patterns the field already ships (Langfuse-style trace/expand, OTel semconv, dataset/experiment loops); build only what is ours. OA-10 reorganizes the surface into two planes — GOVERN (what the factory runs on) and MICROSCOPE (observe → tweak → replay one request) — and specifies the five panels below against the code, verified at 5302ff1. Companion: cwf-agent-control-plane-blueprint-v2.1.

01 The two planes

The reorganizing move. Same tabs, two intents: configure the system vs inspect one request. This is the frame every panel hangs from.

GOVERN

what the factory runs on · global · gated · persistent
  • Rules — the governed rule instances (domain_rules) the agent reads.
  • Kinds — the structural contract (rule_kinds): CORE locked-to-code, SOFT DB-editable.
  • Providers · MCP · Routing · Users — the "govern grammar" panels (same list + detail + gated-action shape).

MICROSCOPE

inspect one request · observe → tweak → replay
  • Inspect (← Telemetry) — observe: the SOTA event list now; the 14-stage trace tree after F-obs.
  • Tweak (← Lab) — the session read-path overlay; per-request tweak fuses into Replay.
  • Replay (new · 0/14) — re-run + diff; the empty-completion is its first customer.

02 Cross-cutting rules — apply to every panel

Panel primer every panel · top

An in-page primer at the top of each panel: what it controls · which tables · WHERE in code · lifecycle — code-accurate, with pointers (e.g. structure → coreSchemas.ts, instances → domain_rules, emission → chat.ts). So a developer knows exactly where to look and never traces the codebase or hunts a needle in a span.

SOTA UI bar no amateur tables

Clean, mainstream patterns. Equal-width aligned columns, no text clipping, expandable rows, rounded numbers (no 15-digit cost), sortable + sticky headers, filter/search, export where data-heavy. Copy the field's shipped patterns; don't invent.

Govern | microscope split two intents

Never mix "configure the system" (global, gated, persistent) with "inspect one request" (ephemeral, session). The sidebar groups them; a panel belongs to exactly one plane.

Determinism / soft split visible §8

Where a panel governs both correctness and advisory content, the two must look different because you can do different things. CORE (locked, poison-proof) vs SOFT (editable) is the canonical case — Kinds makes it visual.

04 Inspect — the locked telemetry SOTA requirements

01Expand-on-click, dual view. A row is a summary; click expands the full record in two synchronized views — human-readable key/value + raw JSON — with copy-JSON.
02No payload column. The payload never clips a table cell; it lives only in the expanded row.
03Equal-width, aligned columns; numbers right-aligned monospace; sortable; sticky header.
04Rounded cost. $0.0028, not 0.00280559999… — the full precision (if ever needed) lives in the expand.
05Time-range picker + export of the selected window.
06Type filter (message · llm_call · tool_call · error) + free-text search; error rows highlighted.
07Trace-id correlation (via F-obs OTel trace id) — the bridge that turns the list into the stage tree and joins it to logs + replay.

05 Sequencing — what ships when

Now — UI + small additions

  • Kinds — pure UI, zero backend.
  • Rules — UI over existing endpoints + one small ready-signal (status enum → migration).
  • Inspect list — SOTA telemetry list over telemetry_events.
  • Tweak overlay — legible labMode; new tweak points are small additive fields.
  • Replay Part B — empty-completion experiment; inputs from messages, tools stubbed from raw_tool_results; task-fn + deterministic scorer.

F-obs gated — OA-8 (host placement + serverless egress)

  • Inspect stage tree — the 14-stage per-request trace via OTel spans.
  • Single joinable trace id — OTel trace id as SSOT; folds the session_id reconciliation (three uncorrelated ids today) into F-obs, never a standalone patch.
  • Replay Part A — isolated mid-pipeline stage replay + diff (needs captured stage I/O).

06 Decisions — resolved & open

Resolved · the parked stage-10 question

Parked: is tool-loop (stage 10) replay a first-class BUILD or deferred? Neither — a third, cheaper answer. messages.raw_tool_results already stores tool results, so tool-loop replay is a stub-from-recorded-results: no live ARMES re-hit, no F-obs. Because the empty is LLM-stage-correlated (tool-composition exonerated), stubbing tools is not only cheap but correct — it isolates the real variable. Sealed into blueprint v2.1.

Named trap · the three uncorrelated ids

conversationId (persisted, message) · traceId 8-char (chat.ts:392, logs only, not persisted) · session_id (chat.ts:451, on telemetry but per-turn, not conversationId, uncorrelated with the log traceId). Today a telemetry row joins to neither its log lines nor a stage tree. Do not standalone-patch — the OTel trace id becomes SSOT and folds this in at F-obs.

Open decision · Inspect cross-user read

Today telemetry_events RLS = own-rows only, so Inspect is personal. Real debugging wants super_admin to inspect any user's request → a small service-role admin read (as rules/versions already do). Committed recommendation: add it (structure → code, gated). Awaiting Maymun's confirm.

07 Next — into the build loop

This scope → gated AG phase prompt(s), one at a time (the loop). OA-10 is large; the natural split follows the sequencing above: a govern-plane UI phase (Kinds + Rules, both mostly-UI) and an Inspect+Tweak+Replay-Part-B phase can proceed now; the F-obs-gated pieces wait on OA-8.
