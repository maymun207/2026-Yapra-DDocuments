Who may change what, where, and how it deploys — the maker-checker governance model

rev 2 · 2026-06-28
HEAD 780018a
design + current state
The model is not bespoke — it is textbook separation-of-duties (maker-checker) laid over dev/prod environment isolation, and the project already implements half of it (drafts → an unbypassable eval-gate → published). A power_user (developer) is the maker: it edits drafts and previews them in its own session only (dev). A super_admin is the checker + deployer: it publishes globally (prod) and manages users. The eval-gate is an automated impartial second checker that binds even super_admin — so no single human can both make and ship, and no one can ship poison.

The three roles · current → target

Today the taxonomy is super_admin / domain_editor / user, where a scoped domain_editor can publish globally. The target renames/repurposes the editor tier to power_user and removes global publish from it — the one deliberate change, and the one that makes the model true SoD (the maker cannot also be the shipper). The per-backend scope survives as an attribute, not a role.

◆ the SoD lives in three rows

rule:publish:global, user:manage, config:global are super_admin-only. A power_user can make (draft + session preview) but never ship. That single cap is the entire separation-of-duties guarantee — encoded as permissions, enforced server-side, not as UI conditionals.

The maker-checker pipeline · state machine

This reuses the existing draft → eval-gate → published machinery verbatim. The only additions are the session-preview state (dev) and binding the publish action to super_admin.

Review verdict, promote to published. Writes rule_versions + rule_audit.

side transitions

reset-to-reference (super_admin): rewrites the code baseline as a new published version — never a delete; history intact, rule_audit(action='reset'). rollback (super_admin): re-opens an old version as a draft that must re-pass the gate. reject at ③: the draft stays a draft; nothing ships.

Session-preview · how a maker's change stays in dev

The load-bearing mechanism that makes "changes for my own session" real — and keeps them out of prod.

mechanism

Reuse the existing per-request override channel (the same one forceProvider rides). A power_user's chat request carries a flag: previewDrafts: [ruleId…] or labMode: {routingBypass, knowledgeSource:'floor'}. For that request only, getDomainContext / the tool filter read the draft / floor / full-set instead of the global published baseline.

Invariant — the overlay is read-only against global: session-preview changes a single user's read path; it issues no write to domain_rules.published, rule_kinds, or tool_category_cache global state. Promotion to prod is exclusively the super_admin publish path through the gate.

Always visible, always audited: a session in Lab/preview shows a persistent banner ("SESSION · dev — not global"), and entering it emits a telemetry event. It auto-expires with the session. No silent, sticky, global toggle.

User management · the root of trust · start here

Currently READ-ONLY (UsersTab) — role/scope assignment is done via the Supabase dashboard because a direct browser write would bypass RBAC. The target turns this into the gated heart of the system, with the guardrails mainstream RBAC mandates.

Gated server endpoint only

Create / delete / assign-role / set-scope flow through /api/admin/users under the service role. Never a direct client write — that would bypass RBAC.

Anti-lockout / no self-escalation

A super_admin cannot demote or delete itself or the last remaining super_admin (the classic "except herself" SoD rule). Guarantees the system can never be locked out of administration.

Least-privilege default

Every new user is created as user. Elevation is an explicit, deliberate action — never the default.

Audit every change

actor · target · old→new role/scope · reason · timestamp → an immutable audit row (mirror the rule_audit pattern). High-risk grants (super_admin) get an explicit confirmation step.

Capability-driven UI

The frontend asks "what may this user do" and hides/disables what the role can't. A power_user never sees an enabled "Publish global" or "Manage users" button.

Future: JIT elevation

Time-bounded, approved temporary elevation for one-off needs (e.g. prod debugging) instead of permanent grants. Designed-for, not built now.

Design direction · modern, mainstream, capability-driven

Admin shell + environment indicator

Persistent left nav (Users · Rules · Kinds · Routing · Telemetry · Lab) + top bar with a role badge + environment flag: "GLOBAL · prod" for super_admin, "SESSION · dev" for power_user. The flag prevents the "didn't realize this was global" footgun.

Real data tables

Scrollable containers + sticky headers (fixes the Kinds-doesn't-scroll bug), search/filter, pagination, row actions, and proper loading / empty / error states — not bare lists.

Capability-driven controls

Buttons reflect permissions: disabled + tooltip ("requires super_admin") rather than hidden-or-crash. One capability query, no scattered role conditionals.

Inline governance affordances

Each tab explains how to edit, how reset works, and labels CORE-locked vs SOFT-editable and gated vs advisory. The existing gate-verdict teaching surface plugs in here.

One design system

A consistent component set (shadcn/ui-class) over the project's dark technical aesthetic — tokens, spacing scale, typography — replacing the current ad-hoc styling.

Diff & history surfaces

Version diff (compare two rule_versions payloads), audit timeline (rule_audit), and a one-click reset-to-reference — the governance story made visible.

Invariants & traps · non-negotiable

⚠ the four that must hold

1 · The eval-gate binds everyone, super_admin included. There is no "god-mode publish." The human checker is itself checked by the machine checker.

2 · Session-preview never writes global. A maker's dev overlay changes only its own read path. A dev→prod leak would be the most dangerous bug in this system.

3 · Anti-lockout is absolute. The system can never be left with zero super_admins; no one can demote/delete the last one or themselves into lockout.

4 · Don't over-engineer to ABAC/PBAC. RBAC + a backend-scope attribute is the right fit at this scale. Full attribute/policy engines are premature.

known tradeoff — the super_admin bottleneck

Strict maker-checker means one checker can become a throughput bottleneck. Accepted for now (safer, matches intent). If it bites, add a scoped-publisher permission (a trusted power_user may publish its own backend) — as a permission, not a new role. Permissions are atomic; roles are bundles.

Implementation sequencing

3-role model + permission checks; gated /api/admin/users (create/delete/assign) with anti-lockout, least-privilege default, audit; capability-driven UI gating. Start here — everything hangs off "who can do what."

The chassis: nav + role/environment badge, scrollable/searchable tables, loading/empty/error states, one design system. Fixes the "baştan savma" UX.

Reset-to-reference buttons (endpoint exists), version diff + rollback UI, CORE/SOFT + gated/advisory labels, inline how-to-edit help.

4

power_user session-preview + Lab mode

The dev-environment overlay (draft preview in own session) + routing-bypass / knowledge-source toggles — the mechanism that also unblocks correct, apples-to-apples acceptance testing.

View/edit/clear learned mappings; folds into steps 3–4. (The OEE-uncategorized fix itself is a code change in Phase F, not a panel edit.)
